Los cubitos, uno por uno

Cada cubito se apoya en el anterior

Léelos en orden. Los marcados en rojo son las dos mejoras nuevas que encontré al investigar.

  1. 1

    El problema

    Una compra no es una sola cosa. Son varios pasos, y casi todos hablan con alguien de fuera: el banco, la paquetería, el correo. Rails sabe deshacer cambios en tu base de datos con ROLLBACK, pero no puede pedirle a Stripe que olvide un cobro.

    ROLLBACK sí llega aquíTus tablas: pedidos, stock, usuarios.
    ROLLBACK no llega aquíStripe, la paquetería, el servidor de correo, el banco.
  2. 2

    La receta tiene nombre

    Si el servidor se apaga, otro trabajador tiene que continuar, y para eso necesita encontrar la receta. Por eso la saga se define una vez con un nombre y se inicia por ese nombre. Un bloque escrito dentro de un controlador vive en la memoria de ese proceso y muere con él.

    # app/sagas/checkout.rb: se define una vez
Durable.define :checkout do |flow, order_id:|
  # pasos...
end

# en cualquier parte: se inicia por nombre
Durable.start :checkout, order_id: 7

    Esto corrige el Durable.run en línea de la versión de Gemini: ese bloque no se podía retomar después de un apagón. Sigue sin hacer falta crear clases.

  3. 3

    El cuaderno

    Cada paso terminado se anota en una tabla de tu base de datos: qué paso fue, si salió bien y qué devolvió.

    Un truco importante: el resultado de un paso siempre se lee del cuaderno, también la primera vez. Así la primera ejecución y una relectura se comportan igual, y lo que funciona en tus pruebas también funciona después de un apagón.

    ✔reservar_stock{"reservado": true}
    ✔cobrar{"id": "pi_381"}
    —despachar

    Por eso los resultados usan llaves de texto: pago["id"], no pago[:id]. El cuaderno guarda JSON, y el JSON no conoce los símbolos de Ruby.

  4. 4

    El apagón y la relectura

    Cuando un trabajador nuevo retoma una saga, vuelve a correr la receta desde arriba. En cada paso mira el cuaderno: si ya tiene ✔, no lo ejecuta y usa el resultado anotado. Continúa en el primer paso sin ✔.

    Trabajador #11 ✔2 ✔apagón
    Trabajador #21 saltado2 saltado3 ✔4 ✔
    Regla de oroTodo lo que toca el mundo va dentro de un paso. Lo que queda fuera se ejecuta otra vez en cada relectura: leer está bien; escribir, cobrar o enviar, no.
  5. 5

    El número de ticket

    Queda un hueco peligroso: el trabajador llamó a Stripe, Stripe cobró, y el servidor se apagó antes de anotar ✔. Al releer, ese paso no tiene ✔ y se ejecuta otra vez.

    Para eso cada paso recibe un ticket que siempre es el mismo, por ejemplo checkout-7:cobrar. Se lo pasas a Stripe como idempotency_key en las opciones de la petición, y Stripe responde «ya cobré con ese ticket» en lugar de cobrar otra vez.

    flow.step :cobrar do |ticket|
  intent = Stripe::PaymentIntent.create(
    { amount: order.total_cents, currency: "mxn",
      customer: order.user.stripe_id, confirm: true },
    { idempotency_key: ticket }   # opciones de la petición, no parámetros
  )
  { "id" => intent.id }
end

    El ticket solo protege si el servicio de fuera lo entiende. Stripe lo hace; si otro servicio no, ese paso podría repetirse. El escenario «Apagón en el peor momento» del simulador muestra este caso.

  6. 6

    Deshacer en reversa

    Si un paso falla y no tiene arreglo, la saga deshace lo que ya hizo, empezando por lo último, como cuando desapilas cubitos: el de arriba sale primero. Cada paso declara cómo se deshace con undo:.

    Ida1 Reservar2 Cobrar3 Despachar ✖
    Vuelta2 Reembolsar1 Liberar stock

    Deshacer también lleva su propio ticket, porque el servidor puede apagarse a mitad de un reembolso. Si tu undo recibe un segundo parámetro, la gema le pasa ese ticket: checkout-7:cobrar:undo.

  7. 7
    Mejora nueva

    El paso atómico: exactamente una vez

    Cuando un paso solo toca tu propia base de datos (apartar stock, cambiar el estado de un pedido), se puede hacer algo mejor que el ticket: ejecutar el paso y anotar el ✔ dentro de la misma transacción. O pasan las dos cosas o ninguna, así que el paso ocurre exactamente una vez, aunque el servidor se apague en el peor momento.

    UN SOLO COMMIT stock − 1pedido: reservadocuaderno: ✔ reservar_stock 
    flow.transaction :reservar_stock,
  undo: ->(_resultado) { order.release_stock! } do
  order.reserve_stock!
  { "reservado" => true }
end

    La idea viene de DBOS, una librería de ejecución durable para Python y TypeScript que hace esto sobre Postgres. Solo sirve para pasos que tocan la misma base de datos donde está el cuaderno.

  8. 8
    Mejora nueva

    El punto de no retorno

    Algunos pasos no se pueden deshacer: un paquete que ya salió, una transferencia SPEI ya enviada. En la teoría de sagas se llama paso pivote. Antes del pivote, si un paso falla sin arreglo (después de sus reintentos), se deshace todo. Después del pivote ya no tiene sentido deshacer: los pasos que siguen se reintentan hasta lograrlo.

    Reservarse deshace
    Cobrarse deshace
    Despacharno retorno
    Emailse reintenta
    flow.pivot :despachar do |ticket|
  envio = Carrier.ship(order.id, reference: ticket)
  { "guia" => envio.tracking_number }
end

    Un email que falló no justifica devolver el dinero de un paquete que ya va en camino. Esto reemplaza la «compensación legal» que Gemini inventó para SPEI. Fuente: patrón Saga en Azure Architecture Center.

  9. 9

    Dormir y esperar

    Para esperar 3 días, el trabajador no se queda despierto. Anota en el cuaderno «despiértame el 8 de octubre», termina y libera todo. Ese día, un trabajador relee la saga (cubito 4), salta lo hecho y sigue.

    Esperar un evento de fuera funciona igual. Por ejemplo, la confirmación de identidad de un proveedor: la saga duerme hasta que tu webhook avisa con Durable.signal.

    flow.sleep :esperar_entrega, 3.days
kyc = flow.wait_for :kyc_listo, timeout: 2.hours

# en el controlador del webhook
Durable.signal "prestamo-42", :kyc_listo, "verificado" => true

    Una saga dormida no ocupa memoria: es una fila en la tabla. Por eso no hacen falta las Fibers que proponía Gemini.

  10. 10

    El buzón

    Durable.start escribe en tu base de datos la nota «empezar esta saga». Si lo llamas dentro de la transacción donde creas el pedido, los dos se guardan en el mismo COMMIT: o existen ambos, o ninguno. Después del COMMIT se encola el trabajo.

    Si el servidor se apaga justo entre el COMMIT y el encolado, un barrendero que pasa cada minuto encuentra la nota sin trabajador y la encola.

    Order.transaction do
  order = Order.create!(order_params)
  Durable.start :checkout, order_id: order.id
end

    El buzón es la propia fila de la saga. No hace falta una tabla aparte.

  11. 11

    La alarma de receta cambiada

    Si cambias la receta mientras hay sagas a medio camino (por ejemplo, insertas un paso nuevo entre cobrar y despachar), la relectura ya no coincide con el cuaderno. En lugar de adivinar, la gema se detiene con un mensaje claro:

    ActiveDurable::RecipeChanged: la saga checkout-7 esperaba el paso
:despachar y encontró :verificar_direccion

    Es la versión honesta de los «Fuzzy Checkpoints» de Gemini: primero detectar el problema. Más adelante se puede añadir versionado de recetas.

Todo junto

El checkout completo

Así se vería la receta del simulador con todos los cubitos. Los números en los comentarios remiten a cada cubito.

# app/sagas/checkout.rb
Durable.define :checkout do |flow, order_id:|          # 2: receta con nombre
  order = Order.find(order_id)                          # 4: solo lee; se repite en cada relectura

  flow.transaction :reservar_stock,                     # 7: atómico, exactamente una vez
    undo: ->(_r) { order.release_stock! } do            # 6: cómo se deshace
    order.reserve_stock!
    { "reservado" => true }
  end

  flow.step :cobrar,
    undo: ->(pago, ticket) {                            # 6: deshacer, con su propio ticket
      Stripe::Refund.create({ payment_intent: pago["id"] }, { idempotency_key: ticket })
    } do |ticket|
    intent = Stripe::PaymentIntent.create(
      { amount: order.total_cents, currency: "mxn",
        customer: order.user.stripe_id, confirm: true },
      { idempotency_key: ticket }                       # 5: el ticket
    )
    { "id" => intent.id }                               # 3: guarda solo lo que necesitas
  end

  flow.pivot :despachar do |ticket|                     # 8: punto de no retorno
    envio = Carrier.ship(order.id, reference: ticket)
    { "guia" => envio.tracking_number }
  end

  flow.step :email_confirmacion do                      # 8: después del pivote, se reintenta
    OrderMailer.shipped(order.id).deliver_now
    { "enviado" => true }
  end

  flow.sleep :esperar_entrega, 3.days                   # 9: duerme sin ocupar memoria

  flow.step :pedir_resena do
    ReviewMailer.ask(order.id).deliver_now
    { "enviado" => true }
  end
end

# app/controllers/checkouts_controller.rb
def create
  Order.transaction do                                  # 10: el buzón
    @order = Order.create!(order_params)
    Durable.start :checkout, order_id: @order.id
  end
  render json: { id: @order.id, estado: "procesando" }
end

Cómo sabremos que funciona

El probador de apagones

Probar una saga una sola vez no demuestra nada: los errores aparecen cuando el servidor se apaga en un momento concreto. Por eso la gema traerá un ayudante de pruebas que corre la saga una vez por cada punto donde podría apagarse: antes de cada paso, después de llamar afuera pero antes de anotar, y después de anotar. Al final de cada corrida revisa que nada se haya hecho dos veces y que la saga haya terminado completa o deshecha por completo.

it "sobrevive a un apagón en cualquier punto" do
  ActiveDurable::Testing.crash_everywhere(:checkout, order_id: order.id) do |saga|
    expect(FakeStripe.cobros_por_ticket.values).to all(eq 1)
    expect(saga.estado).to eq("completada").or eq("deshecha")
  end
end

Esto también es lo que más vende una gema así: el usuario puede demostrar con sus propias pruebas que su saga aguanta apagones.

La pregunta de Rust

¿Y Rust?

Respuesta corta: no en esta gema. Sí en una segunda gema donde Rust sea la razón de existir.

RubyUna cocina con una estufa. Alcanza para casi todo lo que hace una app Rails.
RustUn horno industrial. Vale la pena si vas a hornear mucho pan: cálculo pesado, mucha memoria, millones de operaciones.
ActiveDurablePasa casi todo el tiempo esperando entregas: la respuesta de Stripe, la de la base de datos. Casi no hornea.

Para tu carrera: en una entrevista te van a preguntar «¿por qué Rust?». Si la respuesta es «porque quería», resta. Si es «medí, aquí está el benchmark, es 20 veces más rápido», suma mucho.

El caso real: el SDK oficial de Temporal para Ruby sí usa Rust, con Magnus y rb-sys, como proponía Gemini. Lo hace para compartir el mismo motor con sus SDK de otros lenguajes, no por velocidad.

El plan: buscar 3 o 4 ideas de gema donde Rust sea indispensable y verificar que no existan ya. Una idea ya quedó descartada: Bloom filters, porque bloom_fit ya existe, es nativa y tiene más de un millón de descargas.

Lo que te hace mantenedor de gemas no cambia con el lenguaje: publicar, versionar, escribir el changelog, mantener la CI verde y responder issues. Eso lo vas a practicar desde ActiveDurable.

Siguiente paso

Manos a la obra

La primera sesión de trabajo, en orden. Cada paso termina con algo que se puede ejecutar.

  1. Crear el esqueleto de la gema con bundle gem active_durable en una carpeta tuya, por ejemplo ~/TechProjects/active_durable.
  2. Montar una app Rails mínima de pruebas dentro de la gema, con PostgreSQL.
  3. Crear las 3 tablas: sagas, cuaderno y señales.
  4. Escribir la primera prueba: «un paso anotado no se repite al releer».
  5. Programar Durable.define, Durable.start y flow.step hasta que esa prueba pase.
Pregunta abiertaSi Stripe no responde (un timeout), no sabemos si cobró o no. ¿Deshacemos ese paso, o lo repetimos con el mismo ticket para averiguar qué pasó? Lo decidimos antes de programar las compensaciones, porque cambia la forma de la API.

Antes de crear nada te voy a preguntar en qué carpeta. Vamos de a un cubito por vez, y te explico cada pieza antes de escribirla.
